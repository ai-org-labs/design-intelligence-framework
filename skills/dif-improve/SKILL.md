# dif-improve

Read the existing design and findings as evidence. Identify causes, protected user outcomes and affected targets. Generate both a conservative correction and a radical reorganization with distinct migration risks. Respect hard constraints; keep condition-changing ideas hypothetical.

Retain source candidate IDs, create new IDs for branches/merges, increment revision for changed designs, and record change reasons. Map each change to affected requirements, screens, flows and components. Re-evaluate affected targets and their dependents; use full review when scope is unclear. Keep earlier evidence and mark stale results instead of overwriting history.

Produce actual revised design artifacts when tools permit; otherwise state that the image remains unavailable and provide the layout specification. Compare before/after on design quality, feasibility, business value, migration risk and expected effect. Do not describe an expected improvement as empirically measured.

When improving visual appeal, preserve the product's identified signature and state the intended impression. Refine a representative screen through a concrete visual critique: focal hierarchy, type scale, spacing, color roles and component consistency. Show the revised image alongside the source and explain the few changes that matter. Do not equate more decoration, fashionable styling or a larger redesign with better design. Treat human preference and measured task performance as separate feedback.

Show the main before/proposed-after visual inline and summarize alternatives in a compact comparison table. Use a screen/layout view for visual changes and a flow diagram for navigation or state changes; choose what explains the change rather than adding decoration. Label proposed visuals clearly and connect changes to finding IDs. Lead with a short recommendation and next-decision bullets, linking full evidence and detailed rationale separately. If rendering is unavailable, use a labeled text diagram and preserve the limitation. Keep unknowns visible and follow the user's requested level of detail.

Only a human can adopt, partially adopt, merge or reject. Record the actual statement and provenance; leave pending if none is available. A proposed reusable lesson stays a knowledge candidate until human promotion; private project information must not move into public knowledge. Works without CLI or other skills. Respond in Japanese or English and report budget exhaustion honestly.
