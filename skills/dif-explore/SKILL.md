# dif-explore

Use the request/intake as input. Return in the user's language. Generate conventional and innovative options; for existing UI, include conservative and radical improvement. Vary interaction model, audience priority, information hierarchy or journey, not only colors. Adapt candidate count to complexity and budget; compare at least two viable alternatives when possible.

For each option record stable ID, concept, audience hypothesis, expected effect, explicit assumption IDs, hard/soft/resource constraint checks, risks, cost and distinguishing tradeoffs. Describe comparison axes selected by the user or state your chosen axes. Deduplicate options with the same interaction and hierarchy, preserving meaningful differences in the comparison.

When visual identity or appeal is part of the request, explore two or three visual directions within the budget. Define the intended impression, audience fit, recognizable traits to preserve, and specific visual mechanisms (type scale, spacing rhythm, contrast, composition, shape or motion). Compare the same screen and content, not unequal feature sets. These are visual studies; do not count them as distinct interaction candidates solely because their styling differs. If references are available, identify what makes them work and record their source; do not invent reference research or copy a brand's identity. Without references, label directions as original hypotheses. Do not force a full visual exploration for a narrowly scoped bug review.

Reject or label hypothetical any option that fails or cannot establish a hard constraint. If all choices fail, show the contradiction and condition changes needed; never invent compliance. Shortlisting is a recommendation, not human adoption. No CLI or other skill is required. Return a comparison table plus undecided questions; no aggregate score across quality, feasibility and value.
