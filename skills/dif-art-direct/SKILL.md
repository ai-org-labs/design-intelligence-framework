# dif-art-direct

Deliver design proposals, not a promise to explore later. Work in the user's language. Read [proposal method](references/proposal-method.md) for visual work. This skill is standalone; no CLI, provider, network or other skill is required. Without a renderer, provide explicit composition specifications and mark images unavailable rather than claiming a finished visual proposal.

Translate product meaning → intended audience response → visible design decisions. Establish the actual product, user task, brand constraints and delivery surface from available evidence. Preserve existing identity where required. Branch reasonable assumptions rather than blocking routine exploration; ask only when the answer would change the direction materially.

Inspect relevant references when available, including actual imagery and interactions rather than summaries alone. Record source and what was really observed. Extract transferable mechanisms, not a brand's look. A curator's explanation is attributed opinion, not the agent's own visual observation. If access fails, continue with original hypotheses and label the limitation.

Produce a small set of genuinely different visual directions on comparable content and viewports. State the distinctive idea, visible mechanism, task fit and sacrifice for each. Render representative screens with at least one narrow layout when possible. Do not substitute mood words, color swatches or process diagrams for actual screen proposals. Visual directions need not use different user journeys; do not mislabel them as a complete interaction-design package.

Inspect the rendered artifacts, identify specific weaknesses and revise the provisional favorite at least once when resources permit. Show the change and explain its reason. Never apply uniformity, minimalism, white space or fashionable styling as unconditional rules. Deliberate variation can create hierarchy or character; justify it in context.

Present actual images inline, a concise recommendation and a tradeoff table. Link detailed rationale, reference provenance and implementation notes. Separate creator critique, human preference, task performance and adoption. Do not ask whether to start making proposals after the user has already asked for them. Stay within scope: a proposal does not authorize product deployment, asset purchases or changes to a live product.

Finish the selected direction beyond its hero screen: define semantic light/dark colors, material/edge/elevation choices, optical alignment and component state details. Specify how composition changes with available width/height, rotation and text scaling. Motion needs purpose, trigger, duration/easing, interruption and reduced-motion fallback. Show detail views or a playable sample where useful; avoid decorative texture or movement without a product reason. Distinguish viewport/DPR simulation from physical-device sharpness and native behavior.

Make typography concrete: compare the same Japanese/Latin content in display, body, label and numeric roles; specify family/fallback, actual weights, line height and spacing. Distinguish rendered fonts from declared names. Carry font delivery, licensing, scaling and implementation constraints into the recommendation; a beautiful specimen alone does not establish production fit.
