# Design Agent 要件定義書

- **Version:** 0.3.0 (Draft / requirements baseline)
- **Date:** 2026-10-10
- **Name:** 正式名称未定（仮称 Design Agent）
- **Status:** ヒアリングで確定した方針を統合した要件ドラフト。設計・実装・性能を実証したものではない。

## 1. 概要と目的

CX・UX・UIに関する専門知識を用いて、自然言語・仕様書・既存画面・ソースコード等から、比較する価値のある複数のデザイン案を提案するオープンソースの設計エージェント。設計意図、根拠、制約、品質評価、改善案、採否・変更履歴を追跡できる。**設計提案型**であり、人間が採用判断を行う。

### 1.1 解決する課題

1. デザイン案の幅・多様性が不足する。
2. UI/UX品質が安定しない。
3. 専門知識が不足していて適切な設計判断が難しい。
4. 設計の理由・根拠が説明されない。
5. デザインの良否を検証しづらい。
6. 画面間・設計成果物間に一貫性がない。

### 1.2 基本原則

- **Proposal-first:** エージェントは提案・比較・改善を担当し、採用・重要な例外承認は人間が担当する。
- **Diverge then converge:** 異なる前提・設計思想・ユーザー・操作・ビジュアルを広く探索し、品質・多様性・目的適合性で絞る。
- **Progressive fidelity & validation:** 探索時は軽量・柔軟、詳細化とともに設計データと検証を厳密化する。
- **Explainable and evidence-aware:** 確認済み事実、基準適合、実測、専門的推論、未検証仮説を混同しない。
- **Skills-first, standalone:** Agent Skills単体で主要なテキストベースの設計提案・レビュー・改善を行える。CLI・レンダラ・外部サービスは必須にしない。
- **Portable and open:** 標準Agent Skillsに準拠し、特定LLM、画像生成手段、UIフレームワークに依存しない。
- **Knowledge as Code:** Git管理可能な成果物、判断と根拠、変更履歴、設計知識を扱う。
- **Stable-only publication:** 公式公開機能は基準を満たした安定機能に限定し、未検証機能は正式サポートとして記載しない。

## 2. 対象範囲

### 2.1 最終的な設計粒度

- **CX:** ターゲット、価値提案、接点・リーチ方法、カスタマージャーニー、仮説と根拠。
- **UX:** IA、タスク・ユーザーフロー、画面構成、遷移、エラー・復旧フロー。
- **UI Screen:** レイアウト、ビジュアル、レスポンシブ、情報階層、配色、状態。
- **UI Component:** 部品配置、属性、状態・イベント、操作・フィードバック、アクセシビリティ。
- **Cross-cutting:** 一貫性、制約、評価、設計判断、変更差分。

### 2.2 対応プラットフォーム

Webサイト/Webアプリ、iOS/iPadOS、Android、デスクトップアプリ、クロスプラットフォーム。**MVPはWeb・モバイル共通の設計原則**に範囲を絞る。OS固有ルールの深い対応は拡張対象。

### 2.3 入力

自然言語、要件定義書・仕様書、既存画面・デザイン画像、既存ソースコード、ArchMap/Mermaid等の構造図・フロー図、デザインシステム・ブランド情報、ユーザー調査・利用データ、参考サイト・競合サービス。すべて**最終対応範囲**であり、形式ごとの完全な自動解析をMVPに一括約束しない。読み取れなかった項目、欠損、矛盾、推定を示す。

### 2.4 必須成果物

1. 設計提案書（特徴・設計意図・根拠・比較・評価）
2. 必要な構造図・フロー図（ArchMap/Mermaid等）
3. デザイン画像・モックアップ
4. 機械可読な設計データ

HTML/CSSによる静的プレビューや操作可能なプロトタイプは**初期必須成果物ではない**。モックアップ生成方法は特定ツールに固定しない。描画できない環境では代替設計仕様を提示できるが、画像生成未完了を明記し、4成果物の完成判定を満たしたことにはしない。

## 3. 提案・設計ワークフロー

### 3.1 依頼の理解と不明点

- 前提条件、目的、対象者、制約、既存ルールを抽出する。
- 不足情報がある場合、**前提条件別に複数案**を提示する。前提を事実として扱わない。
- 必須制約違反や重要な不明点は明示し、仮説上の代替案を採用可能な適合案と混同しない。

### 3.2 多様な案の生成

- 設計思想、対象ユーザー、レイアウト・ビジュアル、操作方式・導線の異なる候補を発散生成する。
- 比較軸はAIが選ぶ方式、利用者が指定する方式の双方に対応する。
- 標準的なUIパターンに基づく案と革新的な案をともに含める。
- 重複案を判別し、価値のある差異・想定効果・制約・トレードオフを明示する。
- 候補数は固定せず、品質・コスト・複雑さに応じて適応させる。

### 3.3 段階的な詳細化

1. Explore: コンセプトと仮説を幅広く生成（軽量）。
2. Select: 必須条件、目的適合、多様性、リスク、実現可能性で候補を絞り込む。
3. Visualize: 有力案のフロー・レイアウト・モックアップを制作する。
4. Finalize: 採用・統合案のコンポーネント詳細、状態、根拠、品質評価、追跡情報を確定する。

人間は案の選定、部分採用、複数案の統合、設計ブランチの並行保持を行える。統合後は新規案として整合性検証と品質再評価を行い、由来を保持する。

### 3.4 既存UI改善

- 既存を尊重した保守的改善案と、再構成を含む抜本的改善案をともに提案する。
- 変更影響、品質、実現可能性、ビジネス価値、移行リスクを別々に整理する。
- 問題の原因・改善方法・期待効果を述べ、改善したデザイン案も生成する。

## 4. 制約と専門知識

### 4.1 制約

Hard constraints（必須）、Soft constraints（推奨）、リソース制約を区別する。競合を検出してトレードオフを説明する。緩和可能な条件については条件変更を明示した代替案を出せる。法令・セキュリティ等の必須条件は別途承認・確認なしに緩和されたものとして扱わない。

### 4.2 知識管理

- 標準設計原則、UX/HCI知識、UIパターン等の標準知識を同梱。
- WCAG、Apple HIG、Material Designなど公式情報を適用条件・出典・バージョンとともに参照。
- 組織・プロジェクト固有ルールを拡張可能。
- 過去の設計判断、採否理由、ユーザーテスト、A/Bテストから知識を再利用。
- 公開標準 → 組織 → プロジェクト → 依頼単位のスコープを分離。単純な無条件上書きはしない。
- AIが再利用知識の候補を提案し、正式登録は人間が承認。実測証拠で支持・反証・適用条件・信頼性を更新する。
- 外部の最新トレンドの**自動収集**は初期必須対象ではない。

## 5. 評価と実験

### 5.1 評価カテゴリ

CX整合性、Usability、Accessibility、Responsive/Adaptive、Visual Design、Interaction、Information Architecture、Performance、Consistency、Reliability、Localization、Trust/Ethicsを基本カテゴリ候補とする。別軸として**デザイン品質・実現可能性・ビジネス価値**を独立表示する。評価カテゴリ体系の重複・包含関係は詳細設計時に正規化する。

### 5.2 評価方法とスコア

- **Rule-based:** 規格・形式・数値など機械的に判定可能な基準。
- **AI/Expert:** 設計原則に基づく定性的レビュー。根拠と不確実性を明記。
- **Empirical:** ユーザーテスト、A/Bテスト、実運用データから得る実測。
- 3種類を区別して提示。無条件の平均や未評価項目への架空の点数付与をしない。
- 品質カテゴリ → 特性 → 項目 → 基準の階層を持ち、用途別に項目・重みをカスタマイズする。共通スコアと用途別スコアは比較対象を明示する。
- 評価対象はComponent、Screen、Flow、Product、CX Journey、Change Diff。
- 設計段階ごとに評価し、変更時は影響範囲を選択的に再評価。全件再評価も可能とする。
- 評価対立時はHard制約と優先順位、根拠、適用条件を照合し、残る対立を提示、追加検証・代替案を提案する。

### 5.3 ユーザーテスト・A/Bテスト

テスト計画（仮説、対象者、タスク、測定指標、割当、サンプルサイズ、分析方法）と外部で実施した結果の分析を担当。**実験配信・被験者募集・計測基盤そのものは提供範囲外**。結果の信頼性、サンプル不足、バイアス、不確実性、個人情報保護を扱う。支持・不支持・判断不能を分け、改善案と知識更新につなげる。

### 5.4 問題検出の能力評価

既知の問題セットに対してRecall（見逃し）、Precision（指摘の適合）、誤検出、重大度判定、重大問題の見逃しを別々に計測する。明確な規格違反と解釈の分かれる指摘は区別する。

### 5.5 提案能力の評価

多様性、要求適合性、実用性・完成度、探索効率を独立指標として評価する。実質的な差異と採用に値する候補の質を測る。生成側の創造性と評価側の再現性を分ける。

## 6. Human-in-the-loop / 判断・説明

- AI評価を原則とし、人間が重要判断、評価妥当性、知識昇格を検証する。
- **自動提案優先／標準／逐次確認**などの実行モードを切り替え可能。
- Hard制約の例外、重要な採否、重大なリスク、高い不確実性等に応じて確認を求める。
- 説明は要約／標準／詳細の深さを切り替えるが、内部に保持した根拠は省略・消失させない。
- AI判定、人間の確認、実ユーザーによる実証を別の証拠状態として記録する。

## 7. データモデルと成果物管理

### 7.1 共通情報モデル（独自UI DSLは必須としない）

構造化設計情報をJSON等で扱う。実装候補はJSON Schemaによるバリデーションだが、採用形式・スキーマ詳細は未確定。画面遷移・ユーザーフローは必要に応じてArchMap/Mermaidを使用し、画面描画専用の独自DSLは初期開発しない。

### 7.2 推奨エンティティ（候補）

Requirement、Audience、Goal、Constraint、Journey、Flow、Screen、Component、DesignCandidate、DesignDecision、Evidence、Evaluation、Experiment、Change、Approval、KnowledgeItem。安定IDと明示的な関連を持つ。モデルの正式な語彙と必須項目は詳細設計で確定する。

### 7.3 段階的厳密化

Exploreは仮説と自由記述を許容。Selectで比較軸・根拠、Visualizeで画面・フロー構成、FinalizeでID参照・証拠・必須成果物と整合性を検証する。

### 7.4 保存・変更管理

単一Markdown、複数ファイル、階層フォルダなど出力構成を選択可能。共通情報モデルの意味は維持し、Gitで差分と変更理由を追える。提案・部分採用・統合・分岐の由来、採否理由、評価の差分を保存する。非公開の組織・プロジェクト情報は公開知識に自動移送しない。

### 7.5 完成条件（4条件すべて必須）

1. 必要な成果物が存在する。
2. 要求・フロー・モックアップ・判断・設計モデルが整合する。
3. 適用可能な品質評価が行われ、未評価事項・リスクが明示される。
4. 有力な複数案を比較でき、判断に必要な根拠とトレードオフが提示される。

完成は「最適性の実証」ではなく「採用判断に必要な提案パッケージの成立」を意味する。

## 8. アーキテクチャ・配布・互換性

### 8.1 Skills構成

**統合Skill＋独立した専門Skills**の階層構成。依頼ごとに必要なSkillsと順次/並列処理を選ぶ。単一エージェントで基本実行可能とし、サブエージェント委譲は利用環境が対応する場合の任意拡張。

**専門Skillの責務候補（正式な分割は未決定）：** intake/research、CX、UX/flow、UI/layout、accessibility、evaluation、improvement、experiment、knowledge/provenance。

### 8.2 CLI

Skillsの補助としてスキーマ・参照整合性、制約・規則の機械検証、変更差分、評価データ集計、ベンチマークを段階的に提供する。CLIがない場合でも基本的なテキスト提案・レビューは実行できる。正確な計算・自動検証ができなかった項目は未検証として明示。

### 8.3 提供形態

**確定した必須:** GitHubでOSS公開、Agent Skills、CLI（npm配布）。GitHub Pages、CDN、SDK、Web Playground、MCP、GitHub Actions連携は過去の構想として保持するが、今回の選定では**初期必須から除外**。

### 8.4 互換性・言語

公開Agent Skills仕様に準拠。Claude Code、Codex等の主要環境を検証対象候補とし、対応実績・バージョン・機能制限を公表。基本提案、ファイル保存、画像、外部CLI・委譲などの能力差を区別。日本語・英語の入力、出力、主要ドキュメントに対応。言語間の文字量・改行・ローカライズ差も設計対象。

### 8.5 コスト

要求の複雑さ・重要度に応じて候補数や評価回数等を適応制御。初期探索を軽量化し、有力候補にリソース集中。予算・ツール回数の上限を設けられ、上限到達時は未完了・未検証を報告。計測できないトークン・費用実績は実測値として装わない。

## 9. エージェント品質・ベンチマーク

- **知識の網羅性**、**設計への適用**、**独立レビュー**、**ベンチマーク**の4方向でエージェント自身を検証。
- 標準設計テストケース、意図的に問題を含むUIケース、モデル・Skillバージョン間の比較を提供。
- 期待条件＋評価ルーブリック＋機械検証で唯一の正解に依存しない評価を行う。
- 評価条件、テストデータ、モデル、Skillバージョンを記録。AIの揺らぎを考慮し、必要に応じ複数回評価。
- 品質ゲートは設定可能。標準はWarn、明示設定でEnforce（CLIの失敗終了）。
- AI評価＋人間による検証を組み合わせ、検証の責任と証拠状態を区別する。

## 10. 初期MVPの定義

### 10.1 基本方針

**小さな対象範囲で一連の流れを成立させるVertical Slice**。対象はWeb・モバイルに共通する**会員登録・ログインUX/UI**。本格的な認証基盤は実装しない。

### 10.2 初期MVPの必須シナリオ

ユーザーが要件を与える → AIが不足条件を仮説として分ける → 標準案と新規性のある案を含め幅広く探索する → 候補を絞り込む → 必要なフロー・モックアップ・提案書・構造化データを出力 → ルール・AIレビューで問題を抽出 → 改善版を生成 → 前後を比較 → 人間の採否判断を保存する。

### 10.3 MVPとして着手する構成

- 統合Skill、要件理解/探索/UX・UI/評価/改善の専門能力（Skill分割数は最適化する）。
- 標準設計知識の小規模セットと出典管理。
- 最小共通情報モデルと段階別バリデーション。
- CLI（最小検証器・形式検証・レポート補助）。
- 必須成果物生成契約、未生成/未評価の状態管理。
- 会員登録・ログインの3難易度のテストケース。
- Skills単体での基本動作と主要環境の検証。

### 10.4 初期ベンチマーク

**Level 1:** 最小要求。情報不足の仮説分岐、多様な提案。

**Level 2:** 対象ユーザー・認証方式・制約の詳細が与えられる。要求適合と具体性。

**Level 3:** 曖昧・競合する要求。矛盾検出、Hard制約、トレードオフ、代替案。

各ケースで、期待条件・ルーブリック・機械検証を組み合わせる。検出率・Precision・重大度判定と、多様性・適合性・実用性・探索効率を分けて計測する。

### 10.5 リリース成熟度と成功段階

1. **機能成立:** 最低1つのEnd-to-End設計課題で4つの完成条件を満たす。
2. **品質検証:** 3難易度のベンチマークで設定したゲートを満たす。
3. **実用性検証:** 実際の設計作業で品質・生産性・導入容易性を検証する。

各段階の数値閾値は未決定。**公式OSS公開は安定機能のみ**。未実証の機能を正式サポートとして記載しない。実務効果の実証をどのリリースマイルストーンの必須ゲートにするかは未決定。

## 11. 将来拡張（確定した最終要求だがMVP外）

- CXのリーチ施策・チャネル戦略、全ジャーニーの深い分析。
- iOS、Android、デスクトップ固有の高度な評価ルール。
- 仕様書PDF、画像、各種コードベース、参考サイト等の広範な専用解析パイプライン。
- 実ユーザーテスト・A/Bテストの結果インポートと本格的分析、複数プロジェクトの証拠蓄積。
- 画面群・プロダクト全体にまたがる大規模変更分析、設計の統合・分岐管理の高度化。
- 組織・プロジェクト階層の本格的知識管理、知識提案・承認・反証・更新。
- GitHub Pages / Playground / SDK / CDN / MCP等（採用は改めて決定）。
- 高度なベンチマーク統計・多モデル比較の自動化・運用可視化。

4. 4成果物の具体的なファイル仕様とモックアップ生成不能時の終了状態。

### P1: MVP実装中に詰める

## 13. 非機能要件と公開ポリシー

- 特定LLM・画像生成器・UIフレームワークの必須依存を避ける。
- スキルの文章説明で検証済み機能と未実証機能を混同しない。
- 非公開デザイン資産・テストデータを勝手に公開先へ送信しない。
- 外部資料の出典・引用・ライセンスの扱いを明確化する。
- 評価の推論・実測・自動判定を識別可能にする。
- 公式リリースは、機能テスト・ベンチマーク・互換性・ドキュメントの基準を満たしたものに限定する。
- 未公開の機能はIssue/ロードマップに記載可能だがStable機能として表示しない。
